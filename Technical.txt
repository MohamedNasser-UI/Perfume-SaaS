10. Inventory Architecture

This is where I would be very strict.

Don't make:

inventory_quantity

the only source of truth.

Instead:

Inventory Movement Ledger

is the source of truth.

Example:

Oil Oud

Opening          +5,000 ml
Purchase         +2,000 ml
Sale             -25 ml
Sale             -20 ml
Waste            -10 ml
Adjustment       +50 ml
-------------------------
On Hand          6,995 ml

We can maintain a balance table for performance:

inventory_balances

but every balance must be explainable through:

inventory_movements
11. Weighted Average Cost Architecture

Every inventory item should have:

quantity_on_hand
average_cost
inventory_value

After purchasing:

new_value =
    old_quantity * old_average_cost
    +
    purchased_quantity * purchase_cost

Then:

new_quantity =
    old_quantity + purchased_quantity

And:

new_average_cost =
    new_value / new_quantity

Example:

Existing:

1,000 ml
5 EGP/ml

Purchase:

2,000 ml
6 EGP/ml

New value:

1,000 × 5 = 5,000
2,000 × 6 = 12,000

Total = 17,000

Quantity = 3,000 ml

Average = 17,000 / 3,000

= 5.6667 EGP/ml

This calculation belongs in the backend/domain layer.

12. Sales Transaction

When the user presses:

Complete Sale

the backend should execute one database transaction.

Conceptually:

BEGIN TRANSACTION

1. Validate customer

2. Validate products

3. Calculate customized recipes

4. Calculate component requirements

5. Check inventory

6. Calculate weighted-average cost

7. Calculate selling price

8. Apply order discount

9. Create sales order

10. Create sales lines

11. Create customized configurations

12. Create inventory movements

13. Update inventory balances

14. Create payment

15. Update customer history

COMMIT

If something fails:

ROLLBACK

This is critical.

We don't want:

Sale created ✓
Payment created ✓
Oil consumed ✗

That would corrupt the inventory.

21. Important: Inventory Cost vs Sales Price

I recommend storing both:

cost_at_sale
selling_price

on the sales line.

Why?

Suppose:

Today:

Oil cost = 5 EGP/ml

Tomorrow:

Oil cost = 7 EGP/ml

A historical sale must remain:

Cost at Sale = 5 EGP/ml

It should not change retroactively when inventory cost changes.

Therefore:

Historical transaction
       ↓
Frozen cost snapshot

while the current inventory maintains:

Current weighted average cost
22. Auditability

Every financial/inventory transaction needs an immutable history.

For example:

SALE-000124
Created by: Mohammed
Date: 26-Aug-2026

Inventory movements:

Oud       -25ml
Alcohol   -73ml
Bottle    -1
Pump      -1
Box       -1

We should never simply delete those records.

If something needs to be reversed:

Original transaction
        ↓
Reversal transaction

This is much safer.

30. One Important Change to the PRD

Before we start coding, I would add one architectural concept to the PRD:

Inventory Item

Instead of treating oils, bottles, pumps, boxes, etc. as completely separate inventory engines, create a unified concept:

inventory_items

with:

item_type

such as:

OIL
ALCOHOL
STABILIZER
BOTTLE
PUMP
PACKAGING
READY_MADE
FINISHED_CUSTOMIZED

Then the inventory engine becomes generic.

For example:

Inventory Item
      │
      ├── Oil
      ├── Alcohol
      ├── Bottle
      ├── Pump
      ├── Box
      ├── Ready-made perfume
      └── Finished customized perfume

This will make the system much easier to extend.

31. The Most Important Design Decision

I would build the system around this principle:

Sales are not merely orders. Sales are inventory-consuming business transactions.

For customized perfume:

Sale
 │
 ├── Revenue
 ├── Payment
 ├── Customer history
 ├── Recipe snapshot
 ├── Cost snapshot
 └── Inventory consumption
       ├── Oil
       ├── Alcohol
       ├── Stabilizer
       ├── Bottle
       ├── Pump
       └── Packaging

For procurement:

Purchase
 │
 ├── Supplier liability
 ├── Inventory receipt
 ├── Weighted average cost
 └── Supplier ledger

For return:

Return
 │
 ├── Customer refund
 ├── Inventory
 │
 └── Customized?
       │
       └── Finished Customized Stock
